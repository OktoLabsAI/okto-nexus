# Campanha finita SVC-T14 e SVC-T27 — preparada offline

Este diretório contém uma proposta executável, ainda não executada. A preparação e os testes não criam serviços, tarefas nativas, bancos de runtime, logins nem chamadas ao provedor. O root executará após concluir a preparação M1.

`plan.json` contém todos os argumentos, ambientes, diretórios, nomes das duas tarefas e a porta 58843. `run.py` exige os hashes exatos do plano e do próprio runner, verifica os 984 arquivos pinados na referência da instalação v12, os interpretadores e a ausência prévia das duas tarefas e dos dados. Não importa o runner histórico v3. Os diretórios e resultados privados pertencem exclusivamente a esta campanha.

Cada host percorre seis seleções: instalar em contexto A; iniciar canonicamente a partir do caller B com PATH reduzido; parar normalmente e confirmar saída física pelo handle retido; desinstalar; executar foreground no mesmo home/state; parar normalmente e confirmar a saída física. Total: 12 CLIs, quatro starts, quatro stops, duas instalações e duas desinstalações. Nenhum force, reinício automático, login, setup ou trabalho produtivo.

T14 exige tarefa nativa ativa, executável e working directory da definição, contexto persistido com PATH A, processo real de Python identificado por handle/birth, identidade exata e readiness. Nexus exige project-root A e a configuração explícita. Connector exige o diretório canônico de estado; sua definição não possui projeto de trabalho. O resultado Connector é deliberadamente parcial quanto ao enunciado de projeto de T14 e não qualifica seleção remota de projeto.

T27 exige um banco não vazio criado pelo runtime (`nexus.db` ou `owned-slots.db`), fingerprint de todos os arquivos retidos após stop/saída e igualdade exata depois de uninstall. Só são excluídos os recibos de integração que o código instalado remove: installation/control e, para Nexus, o claim do banco. Qualquer outro arquivo adicionado, removido ou modificado recusa a prova. O foreground posterior usa o mesmo home/state, mesma identidade e nova geração; a tarefa deve continuar ausente. Nexus precisa declarar storage_initialized; no Connector instalado, READY ocorre somente após `await host.ensure_ledger()`. Não se comparam bytes depois de iniciar novamente, pois essa inicialização pode legitimamente modificar os bancos. A campanha não prova conteúdo de trabalho produtivo nem acesso autenticado.

Start pode retornar 3 e ainda ficar pronto: há apenas observação passiva limitada a 180 segundos, sem nova seleção. Stops exigem CLI 0, shutdown_outcome drained e saída física; não há fallback destrutivo. Em falha, o runner publica a recusa e preserva handles/processos ainda vivos em espera passiva, para reconciliação explícita pelo root. Uma CLI bloqueada não é morta por timeout do harness. A campanha não prossegue para novos efeitos depois de uma falha.

Os XMLs de testes são offline. O primeiro registra 21 PASS e uma falha da asserção de tipo Path/string; o teste corrigido compara Path e a rodada final tem 22 PASS. Os testes cobrem os comandos exatos no parser Connector instalado, configuração Nexus, exclusões de uninstall, alterações de dados, divergências de contexto/executável/PATH/projeto e o entrypoint isolado `--help`. Nenhum resultado offline constitui aceite nativo de T14/T27.

Execute somente após revisão do root, com o Python indicado em plan.json, `-I -B -X utf8 run.py execute --expected-plan-sha256 <hash do plano> --expected-runner-sha256 <hash do runner>`. `freeze.json` fornece esses valores. Não executar `prepare.py` novamente depois do freeze. Após execução, publicar apenas a allowlist explicitamente curada de JSONs seguros, nunca stdout/stderr brutos ou os dados de runtime.
