# NS15.03 legacy-to-canonical fallback — October 1, 2026

A new conversational delivery with typed pre-write failure may now select an
approved equivalent canonical endpoint through the existing fallback planner.
Its original sender, workspace, envelope, causal root and logical claim remain
unchanged. Handoffs, result relays, continuations, controls and uncertain native
effects remain excluded by the existing fallback policy.

The persisted retry deadline and bounded attempt budget remain authoritative.
At the deadline, the legacy owner claims the next attempt and invokes canonical
admission inside that same transaction. It never queues the canonical target
for a legacy native worker and never puts a canonical session ID into a legacy
harness foreign key. Successful admission releases the legacy worker epoch;
the R4 outbox owns physical execution. Existing attempt history preserves both
the pre-write proof and selected destination.

Canonical admission revalidates the original equivalence approval as well as
the target policy. An expected refusal rolls back all partial R4 admission rows
to a savepoint, rejects the attempt and releases the safe logical reservation.
Unexpected storage failures roll back the transaction, preserving the original
durable retry. A generic exception remains OUTCOME_UNKNOWN and never transfers.

Public message tests exercise success, unknown outcome, source revocation and
post-admission rollback with fixture-native pre-write proof. The installed
campaign also checks mixed selection, MCP claim exclusion and legacy fallback/
retry regressions. Evidence is generated by `run_ns15_03_fallback.py` and recorded
in `test_runs_20261001_ns15_03_fallback.json`.

This delivers the legacy-to-R4 direction. Re-selection after a canonical attempt
requires canonical non-effect evidence and remains pending; it must not be
inferred from a timeout or from a legacy status label. Native loader removal,
full restore and final provider/platform/release acceptance remain open.
