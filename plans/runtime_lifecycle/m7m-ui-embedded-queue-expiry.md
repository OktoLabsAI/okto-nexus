# M7m: embedded Pi queue deadline through the installed Nexus UI

On 2026-10-18, disposable Nexus 0.3.1 with installed Connector 0.0.10 and Core 0.0.12 ran at `127.0.0.1:8204`. The real Pi 0.87.1 agent `m5m-pi-new` was configured through Agents > Connections as embedded one-shot with maximum 2 parallel instances, 1 warm instance, queue capacity 1, and a 5-second start deadline. The connection test passed; Agents later showed the pool at 1/2 available. Source revisions were Nexus `c448d6d`, Connector `2c2f869`, and Core `9b84aa4`.

The first attempt to send a burst in one Meta-harness tab serialized at the composer. It sent only one long request, which eventually returned `M7_WARM_OK`; it is not used as queue evidence. Three separate Meta-harness tabs were then prepared for the same agent and workspace, and their Send buttons were clicked concurrently. The three intents were two 90-second terminal sleeps and one short exact-marker request. Their actual admission order differed from tab order: the short request used the warm slot and returned `M7_TAB_QUEUE_OK` with 1/1 ACK. The two remaining requests yielded caller-visible `ONE_SHOT_START_TIMEOUT` and `ONE_SHOT_QUEUE_EXPIRED`. Both error payloads reported `execution_started=false`, `possible_effect=false`, and `retry_safe=true`; the queue error reported stage `queue` and the start error stage `opening`. The pool returned to 1/2 available without user intervention.

This reproduces the Connector-local Pi split from M7k on the embedded route, with a real harness and UI submission. It verifies the queue deadline and caller error propagation, not a latency distribution or Codex/Claude behavior. The scoped test fixture and its Pi child process were stopped; no process from that fixture or listener on 8204 remained. The global Nexus instance was untouched.
