# M8 installed CI: Pi bridge timing fixture

Installed matrix [39389028762](https://github.com/OktoLabsAI/okto-nexus/actions/runs/39389028762) on `82c8324` completed 23 of 24 jobs successfully. Windows 3.12 shard 0 reached `test_automatic_pi_bridge_survives_initial_deadline_with_applied_renewal[pi_rpc]` at 15% and remained there until the three-hour job limit canceled it. The prior matrix had passed this same shard. The CI log shows the affected test but does not expose its underlying exception before cancellation.

Isolated Windows reproduction captured `CoreError('AUTH_EXPIRED')` from the test's native-environment preparation. The fixture had shortened the initial local-tool metadata lifetime to two seconds; on a loaded host it expired before preparation completed, leaving the opening `OUTCOME_UNKNOWN`. With a longer lifetime, one isolated run reached the handoff action but crossed the six-second lease deadline between the action and its response, which Core correctly classified as `OUTCOME_UNKNOWN` after possible effect. Those are fixture timing races, not evidence that an unchanged real harness failed. The local reproduction was run with the global Nexus stopped to keep the fixture's fixed loopback port free.

The test now grants 20 seconds for preparation, uses a 30-second renewable lease, and invokes its bridge actions only after the initial metadata deadline has passed **and** an applied renewal leaves more than ten seconds of action-response runway. It tolerates only the transient `LEASE_UPDATE_PENDING` while checking that context. Thus it still proves a Pi native bridge can read context and claim/complete a handoff after initial expiry; it no longer depends on completing those operations inside a two-second startup race. The exact source test passed three consecutive Windows runs after the final condition. No production code, Core or Connector change was made for this CI finding. A complete replacement installed matrix remains the acceptance gate.
