# M5j — Managed handoff claim after a no-effect startup failure

Date: 2026-10-18 UTC. This is a read-only forensic checkpoint from the disposable installed Nexus/Connector/Pi UI fixture. No production instance was running or changed.

During M7i's deliberately delayed pre-Core opening, the Connector lost the original lease authority and Core returned `PRE_EXECUTION_FENCED`. The one-shot call recorded failure with `execution_started=false`, `possible_effect=false`, `retry_safe=true`; the operator received the error in Meta-harness. The canonical `runtime.open` receipt is `FAILED`, `possible_effect=0`, `retry_safe=1`. The bound `turn.submit` has no receipt, and the exact session later reached lifecycle `CLOSED`, lease `CLOSED`. The outbox is `FAILED_FINAL` with no reconciliation. Before the test operator cancelled it, the handoff remained `CLAIMED`, even after its claim lease expired. Handoffs showed “Execution failed”; the operator had to cancel the handoff manually.

The current automatic capacity compensation handles an **unconsumed** reservation (`CANCELLED_NO_EFFECT`). Here the reservation had already reached `CONSUMED` before the opening failed, so that branch cannot reopen the claim. The ordinary lease-expiry path intentionally excludes an unreconciled managed binding. The broadcast scheduler scans `OPEN` handoffs and active unconsumed attempts; it does not independently settle this consumed, no-effect failed claim.

The recovery criteria are the exact Core no-effect receipt, a fenced original producer, proof that the physical session and lease are released, absence of any native turn/result or authenticated handoff decision, and the same claim generation before atomically reopening. The original attempt and failure evidence must remain durable. A bounded per-agent retry/backoff prevents one unhealthy harness from repeatedly reclaiming the broadcast. Ambiguous or possible-effect cases stay claimed for explicit reconciliation. The artificial injection proves the state gap; it does not establish how often natural failures hit it.

Implementation checkpoint: migration 151 retains historical consumed attempts and adds a narrowly proved no-effect view plus a per-handoff/agent retry clock. The bounded broadcast scheduler finds these failed claimed rows; candidate discovery re-reads the exact proof inside its writer transaction, reopens the canonical claim, retires the original attempt as `FAILED_NO_EFFECT` and delays only that agent's next automatic candidacy (15 seconds, doubling to a 300-second cap). A different eligible agent remains available immediately. The proof requires the Core opening's latest `FAILED` receipt with no possible effect and retry safety, the session and lease both closed, a terminal `INITIAL_OPEN_FAILED` turn with no receipt, no result or work decision, and a no-effect one-shot outcome. Uncertain evidence does not enter this path.

Validation: eight focused source cases and eight cases against an installed Nexus wheel passed, including missing/uncertain proof guards and application discovery orchestration. Three selected source integration cases and three against the installed wheel passed for normal discovery and scheduler replay. After making the adapter clock an explicit input, the final wheel passed the eight focused cases plus the candidate-pagination case. Final wheel SHA-256: `a98b2ee35f18d04360306da2291f5a839bf13e9974179d48d4ccb7ab09e5727a`; its archive contains migration 151. The actual migration runner upgraded a disposable copy of the real UI database from 150 to 151, retained the historical committed attempt and passed `foreign_key_check`. A separate proof query against that copy matched the known M7i failure. No new Nexus UI run is claimed for this checkpoint; the embedded/Connector differential and major UI gate remain open.
