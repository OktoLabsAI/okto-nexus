# M5y: receipt loss and recovery with a separate Connector process

Date: 2026-10-18. This closes the remaining local process-boundary comparison identified in [M5x](m5x-differential-evidence-audit.md), without changing the fixed M5 criteria.

The existing cross-process capacity fixture starts a disposable Nexus HTTP server and a Connector daemon in another Windows process (`python -I`). Its native peer is deterministic, while control, lease, dispatch, receipt publication, journal and reconciliation use production code. The helper now accepts a one-time fault that drops the `SUCCEEDED` receipt request **before Server commit**. The test admits a real close operation after one native open/turn, observes the temporary `DISPATCH_CONNECTION_LOST`/possible-effect state, waits for the same durable terminal receipt to reach `SUCCEEDED`, and then waits for the Connector to rejoin `CONTROL_READY` in a newer generation. It asserts one Connector native open, one native close, one canonical close receipt and no second dispatch attempt. The process exits cleanly. The original graceful and abrupt capacity variants remain separate and unchanged in expected behavior.

Installed Nexus 0.3.1, Connector 0.0.10 and Core 0.0.12 were tested with pytest's source path disabled (`-o pythonpath=`): the three cross-process variants passed together; after adding the explicit post-receipt `CONTROL_READY` assertion, the fault variant passed again (**1 passed, 2 deselected**). This is paired with the installed embedded receipt-persistence and cold-restart tests in M5x, which also retain one native effect and recover the original receipt. The earlier real-UI M5t/M5m/M5u/M5v/M5w runs cover Pi availability, reconnection, revocation and preserve-agents reset on both local routes.

The local M5 acceptance outcomes are verified. This test does not claim a physical remote host or a real provider under the injected receipt fault; those are distinct from the already completed real-Pi UI flows. The global Nexus remained stopped.
