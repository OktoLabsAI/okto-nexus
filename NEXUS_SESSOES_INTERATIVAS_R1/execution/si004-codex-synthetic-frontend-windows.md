# SI-004 Windows Codex frontend against a synthetic peer

The operator separately approved starting the installed Codex 0.170.0 frontend against a synthetic loopback WebSocket peer. The executable matched SHA-256 `8d06dc231dba649c7d48d3eecab239c452a1ac498c41dd6492a6f301b90a22ce`. The launcher used an empty temporary profile and project with an explicit child environment, no provider credentials, and no initial prompt. A separate rejecting local endpoint handled normal proxied network traffic. The final run observed one rejected proxy connection. No model execution or native engine was part of the test.

The exact fictitious UUID was selected by `codex resume <id> --remote <loopback>`. The frontend sent the test bearer in the WebSocket authorization header. The peer refused Origin and additional connections. Its synthetic wire test rejected a sibling thread, global thread listing, and turn start. The recorded frontend run authenticated, requested the exact UUID in `thread/read` and `thread/resume`, and rendered a unique synthetic history response in ConPTY. The fixture closed only its launched viewer, observed its exit, and observed the WebSocket disconnect. The fixture had no durable harness process whose survival could be measured.

Earlier runs established two required bootstrap behaviors. Returning a method error for `configRequirements/read` stopped bootstrap. Returning an empty model catalog without an explicit model also stopped bootstrap. The successful fixture used schema-validated local replies for `initialize`, `account/read`, `model/list`, `configRequirements/read`, `collaborationMode/list`, `hooks/list` and `account/bedrock/checkGovCloudRequirements`. It handled `initialized` as a notification and returned an empty skills list. The frontend continued to display the target when the peer refused `thread/list`, `thread/loaded/list`, `thread/goal/get`, `plugin/installed` and `thread/backgroundTerminals/list`.

The wire request for `thread/resume` includes fields for provider, model, paths, config, permissions and history in addition to the target ID. Passing that request directly to the Core-owned app-server would allow those fields to reach the engine. The production adapter needs to synthesize the viewer response from the already-owned context and use only explicitly bounded reads. Global bootstrap replies must be scoped and have no upstream side effects.

The [sanitized observation](si004-codex-synthetic-frontend-windows.json) records methods, parameter names and the result. The fixture's console used separate read and write pipes and a bounded output drain.
