# SI-026 — Processo Claude mantido pelo Core no Windows

O Core pode criar o Claude em um ConPTY e incluir o processo em um Windows Job no mesmo ato de abertura. O processo e as conexões de entrada e saída pertencem ao host. Cada leitor guarda seu próprio cursor, e o Core continua drenando a saída quando nenhum leitor está conectado. Um cursor fora do trecho retido recebe conflito. O encerramento do proprietário segue uma operação separada.

O hook local de prompt verifica um token entregue ao processo, o UUID da conversa, o diretório, o modo de permissão e o conteúdo exato. Cada autorização corresponde a uma operação e pode ser usada uma vez. A função de autorização do host precisa gravar o efeito possível antes de devolver sucesso. Uma falha ou resposta perdida consome a autorização e deixa o resultado para reconciliação. [Referência do comportamento do hook](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)

O ensaio com o wheel instalado abriu o Claude Code 2.1.328 com o histórico já gravado. O catálogo confirmou o UUID e o PID do processo mantido pelo Core. Um erro simulado na autorização retornou HTTP 503 e o Claude bloqueou o prompt antes de chamar o simulador de modelo. Depois de autorizar outra operação, o ensaio começou o turno e soltou o leitor enquanto a resposta estava em andamento. O mesmo processo concluiu o trabalho e outro leitor recuperou o resultado pelo cursor. A repetição da entrada ficou bloqueada e o Claude encerrou com código 0. Um teste separado confirmou que a saída abrupta do host encerra o processo de teste associado ao Windows Job. [Cenários, hashes e resultados](si026-claude-owned-terminal.json)

O ensaio usa leitores locais do Core e autorização simulada, em projeto descartável e sem ferramentas ou provedor externo. O marco dispensa migração. O rollback restaura os commits e os wheels anteriores nos três repositórios.
